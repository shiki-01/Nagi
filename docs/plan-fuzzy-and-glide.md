# 曖昧入力の改善とグライド入力の計画（2026-11-03 草案）

実装前の調査と計画。決定ではない。決定する際は `docs/decisions.md` に H 節として記録する。
他 IME の調査結果は Web 上の要約とソースに基づく。Gboard / SwiftKey / Simeji / ATOK / iOS 標準の内部実装は非公開で未確認。

## 1. 曖昧入力

### 1.1 現状（`docs/decisions.md` H-24 / H-25 / H-73）

- クレート `nagi-fuzzy`。隣接キー表による置換・脱落・挿入・転置、濁点・小書きの付け忘れ。辞書 trie の枝刈り探索。
- M2: 打鍵列（`Stroke`）を保持。`set_layout_geometry` のキー矩形とタッチ位置（相対座標）から、ガウス尤度で置換コストを算出。
- 出力は「もしかして」候補（`CandidateSource::Fuzzy`）のみ。読みは自動置換しない。
- 未実装: M3（LLM 再採点）。評価は実機の体感のみで、数値の評価基盤がない。

### 1.2 他 IME の仕組みとの差

| 仕組み | 他実装 | nagi |
| --- | --- | --- |
| タッチモデル | Gboard はキー中心からのガウス（Goodman 2002 が原典）。キー別のオフセットを個人化する研究あり | ガウス尤度は実装済み。個人化はなし |
| 辞書側の規則補正 | Mozc `KeyCorrector`（「んん」「っっ」等のかな列書き換え、+3000 のペナルティ、位置対応を保持）。azooKey `TypoCorrection`（混同表と DFS、重み 3.5、最大 3 個） | 濁点・小書きは対応。かな列の規則補正は未整理 |
| LM を使った補正 | azooKey `ZenzaiTypoCandidateGenerator`: 置換・脱落・転置のチャネルコスト（α=2.0, β=3.0, γ=2.0）と zenz の対数確率を合算し `score = lmScore − channelCost`。ビーム幅 32、最終 5 件。入力そのままを必ず基準候補に入れる | 未実装（M3） |
| 文脈 | 上記 LM が左文脈を使う | `set_context` で左文脈 20 文字は取得済み。補正には未使用 |
| 学習済みタイピングモデル | Mozc `typing_model_qwerty_mobile-hiragana.tsv` / `typing_model_12keys-hiragana.tsv`（キー列 → コストの表）。用途は未確認 | 未調査 |

### 1.3 改善案

優先順に並べる。

**F0. 評価基盤（先に作る）**
- Mozc `evaluation.tsv` の読みに対し、隣接キー置換・脱落・転置・タッチ座標のずれを注入した入力を生成し、補正候補の top1 / top5 正解率と追加レイテンシを `nagi-eval` で測る。
- 12 キーはフリック方向の誤認識（隣接方向）を注入する。
- これがないと F1 以降の効果を比較できない。

**F1. 文脈込みの LLM 再採点（H-25 の M3）**
- 補正候補の読み（チャネルコスト付き、上位 N ≤ 8）を、左文脈つきで zenz に評価させ、`lmScore − channelCost` で順位付けする。入力そのままの読みを必ず基準に入れる。
- 同期予算内に収まらなければ、現行の辞書スコアにフォールバックする。
- 要調査: azooKey の zenz への入力書式（読みを与えて表記を出すか、タイプ誤りの入力から意図した読みを生成するか）。ソースの該当箇所を読んでから、nagi の zenz 呼び出し（`nagi-infer`）への当て方を決める。
- 影響範囲: `core/engine` の候補生成、`core/infer`。プロトコル変更は不要。

**F2. 高確信時の自動採用**
- 現状は「もしかして」を混ぜるだけ。再採点後のスコア差（補正候補 − 入力そのまま）が閾値を超える場合に限り、Space 変換の第 1 候補に補正を採用する。
- 誤採用に備え、元の読みへ戻せる経路（候補一覧に元の読みを残す）を維持する。閾値は F0 の数値で決める。既定は off から始める。

**F3. 打鍵ごとの確率分布の保持（ローマ字入力）**
- 各タッチについて上位 k キー（k = 2〜3）と確率を保持し、ローマ字 → かな変換を多重化して辞書探索に渡す。
- H-25 の置換コスト方式との差が小さい可能性がある。F0 で F1 の効果を見たうえで、必要なら着手する。

**F4. Mozc typing model の調査**
- TSV の意味と使い方を調べ、nagi の確率モデルに転用できるか判断する。ライセンスと再配布の扱いは「同梱せず別途取得」の方針に従う。

**見送り: キー別オフセットの個人化**
- H-25 は「指の位置を保存しない」方針（プライバシー）。個人化にはタッチ統計の保存が必要で、方針と衝突する。端末内の集計値のみにするか、見送るかは別途決定する。

## 2. グライド入力

### 2.1 対象と前提

- 対象は QWERTY のローマ字入力（`qwerty-kana`）。12 キーは対象外。
- キー矩形は `set_layout_geometry`（H-25）で既にコアへ渡している。座標は相対値の方針を継続する。
- 1 ストローク = 1 語（文節相当）から始める。複数語の連続なぞりは後段。

### 2.2 方式（他実装から）

- 基本は SHARK2（Zhai & Kristensson, 2004）系。入力軌跡と、単語をキー中心でつないだ理想経路を、形状と位置の 2 つの距離で比べ、言語モデルと合わせて順位付けする。
- FlorisBoard `StatisticalGlideTypingClassifier` の構成（ソースで確認）:
  1. 近すぎる点を間引く。
  2. 始点・終点の近傍キーで単語を絞り込む。軌跡長が理想経路の一定倍以内のものだけ残す。
  3. 200 点に再サンプリングし、バウンディングボックスで正規化する。
  4. 形状距離（ユークリッド）と位置距離（マンハッタン）のガウス確率に、単語頻度を掛ける。
  5. 二重文字（促音など）は小さなループを足した理想経路を追加する。
- HeliBoard は閉じたライブラリを使用し、AOSP の gesture 実装は未確認。日本語のグライド実装例（azooKey 等）は見つからなかった。

### 2.3 nagi への当てはめ（私の設計案）

```
フロント: 軌跡収集 (x, y, t) → キー矩形基準の相対座標へ
   ↓ glide_input
コア nagi-glide（新クレート）:
  1. 間引き・再サンプリング・正規化
  2. 始点・終点キーで辞書の読みを絞る（読みをローマ字化した索引）
  3. SHARK2 の形状 + 位置スコア
  4. 上位 N 個の読み（スコア付き）
  5. 各読みを Preedit に入れ、既存の変換（辞書 Viterbi + zenz、左文脈つき）に渡す
   ↓
候補（CandidateSource::Glide）を返す
```

- 日本語固有の論点:
  - 見出し語は読み（かな）なので、ローマ字の理想経路に変換する必要がある。綴りの揺れ（shi / si、nn / n、促音の子音重ね、長音）は、代表綴り 1 つに正規化し、揺れはスコアの許容で吸収する。
  - 英語より語長が長く、見出し語数も多い。絞り込み索引が必須。
  - 文脈（左文脈）は、グライドの読み候補の順位付けに使う（F1 と同じ仕組みを共用できる）。
- プロトコル: 新メソッド `glide_input { points, layout_id }`（要設計）。Swift 型は `typeshare` で生成。
- フロント: iOS は `DragGesture`、Android は `MotionEvent`。タップ・キー長押しポップアップ・スペーススライドとの競合整理が必要。軌跡の描画は別途。
- 設定: `input.glide`（既定 off）。

### 2.4 制約・リスク

- iOS 拡張のメモリ上限は約 177MB（H-6）。索引は mmap で持つこと（辞書と同方式）。
- 目標は 1 ストロークの認識 p95 < 50ms（暫定。実機で再設定）。
- 精度の見積もりは未確認。合成軌跡（理想経路にノイズを加える）でのベンチを先に作る。
- 複数語連続のなぞり、ライブ変換との併用、LLM 無しの精度が未決。
