# グライド入力（なぞり入力）

QWERTY のタッチキーボードで、指を離さずに文字の上をなぞって 1 語を入力する機能のコア側の仕様と、
フロント（iOS / Android）が送る軌跡の形式。計画は `docs/plan-fuzzy-and-glide.md` §2、決定の経緯は
`docs/decisions.md` H-82。**コア側（G0〜G2）は実装済み。フロントの UI は G4 iOS が実装済み（実機・CI 未確認。H-83）、iOS への索引の配布も実装済み（H-84）、G3 Android は未着手。**
合成軌跡での評価だけで、実機の指での精度は未確認。

## 1. フロントがやること

1. キーボードを表示したら `set_layout_geometry` でキー矩形を送る（既存。H-25）。QWERTY の英字キー（英字 1 文字の `text` キー、または中央 `center.text` が英字 1 文字の `flick` キー。
   上段 q〜p だけ上フリックで数字を出す `flick` のレイアウトを含む）が 20 個以上あるレイアウトだけがグライドに使える
   （12 キーのかなは対象外）。`flick` キーからなぞり始めた場合は、そのキーのフリック入力（数字・方向ポップアップ）を取り消す（実機未確認）。
2. 設定 `input.glide = true`（既定 false。コアの設定項目として `get_settings` に出る。グループ「入力」・詳細レベル・iOS 向け）のときだけ、なぞり入力を有効にする。
3. 指を置いてから離すまでの軌跡を集め、離したときに `glide_input` を 1 回呼ぶ。応答は `process_key` などと同じ描画差分
   （`ProcessKeyResult`）。

```json
{"jsonrpc":"2.0","id":7,"method":"glide_input","params":{
  "session_id":"s",
  "layout_id":"qwerty-1",
  "points":[{"x":21.5,"y":38.0,"t":0.0},{"x":24.0,"y":37.2,"t":11.1}, "..."]}}
```

### 点列の形式

| 項目 | 内容 |
| --- | --- |
| 座標系 | **`set_layout_geometry` の `keys`（`x` `y` `w` `h`）と同じ座標系**（キーボード view のローカル座標。左上が原点。単位は問わないが、キー矩形と同じ単位にする）。タップの `touch`（キー内の相対位置 0..1）とは違い、ストロークはキーをまたぐので絶対座標で送る |
| `t` | ミリ秒。ストローク内で単調増加すればよい（原点は任意。`CACurrentMediaTime` や `MotionEvent.eventTime` をそのまま使える）。**現状の認識では使わない**（予約。速度による角の検出などに使う余地） |
| 点数 | 実機のタッチ移動イベントをそのまま送ってよい（60〜120 Hz なら 1 ストローク 20〜200 点程度）。**最大 2048 点**。超えた分はコアが等間隔に間引く。コアは近すぎる点を間引き、200 点に再サンプリングするので、フロント側で間引く必要はない |
| 最小の長さ | 軌跡の長さがキー間隔の 1 倍未満（ほぼタップ）なら認識しない。タップは従来どおり `insert_reading` で送る（フロントが「動いた距離がしきい値以上ならグライド」と判定する。しきい値はフロントで決める） |
| `layout_id` | 任意。`set_layout_geometry` の `layout_id` と一致しなければ（レイアウト切替直後の古い軌跡）認識しない |
| 座標の保持 | 軌跡は認識の間だけ使い、保持しない。ログにも出さない |

### 応答の使い方

- `consumed = false`: 認識しなかった（機能が無効・配置が無い・ひらがなモードでない・タップ相当・候補なし・`layout_id` 不一致）。
  何も変わっていない。フロントは軌跡を捨てる（必要ならタップとして扱う）。
- `consumed = true`:
  - `commit`: 直前の語（入力中だった文字列）の確定。前の語がなぞり入力で、読みを編集していなければ、先頭の候補（変換結果）で
    確定する。編集していれば見えている文字列を確定する。
  - `preedit`: 認識した最有力の**読み**（ひらがな）が入力中（Composing）の文字列になる。
  - `candidates`: 認識した読み（最大 5 つ）を既存の変換（辞書 Viterbi + LLM、左文脈つき）にかけた表記。
    出所 `sources` の先頭が `glide`、`reading` にその候補の元の読み。先頭が最有力の読みの変換結果。同じ表記は 1 つにまとまる。
    `covers` は常に `None`（入力全体を置き換える）。選ぶ（`select_candidate`）と、その候補の**読み**で確定・学習する。
  - 少し遅れて `update_candidates` 通知で、通常の入力中の候補（最有力の読みの別の漢字、ひらがな・カタカナなど）が後ろに足される。
    先頭の `glide` の候補は動かない。
- 続けて Space / `perform_action(Space)` は最有力の読みの変換（Converting）に入る。Enter は入力中の読み（ひらがな）をそのまま確定する
  （通常の入力中と同じ）。
- 1 ストローク = 1 語。次のストロークを送ると、前の語は先頭の候補で確定してから新しい語が始まる（複数語をつなぐ
  連続なぞりは未実装）。

## 2. コアの構成

| 場所 | 内容 |
| --- | --- |
| `core/glide`（`nagi-glide`） | 純粋なロジック。`spell`（読み → ローマ字のキー経路）、`geom`（キー配置・間引き・再サンプリング・正規化）、`index`（読みの索引）、`recognize`（認識）、`synth`（合成軌跡）。依存は `nagi-dict`（索引の構築）と `memmap2`（索引の mmap）だけ |
| `core/protocol` | `glide_input`（`GlideInputParams` / `GlidePoint`）、`CandidateSource::Glide`。Swift 型は `cargo xtask gen-types` |
| `core/engine` | `Engine::glide_input`、`ConversionBackend::glide_readings`、`EngineConfig.glide_input` |
| `core/server` | `glide.rs`（索引と認識器のキャッシュ）、`Pipeline::glide_readings`、JSON-RPC の `glide_input` |
| FFI / JNI | `glide_input` 自体は JSON-RPC 行を流すだけで C ABI の追加は要らない。索引の配布のため FFI に `nagi_build_glide_index` と `nagi_server_new_with_flags`（H-84）。JNI は変更なし |

### 認識の流れ（`nagi-glide`）

1. 前処理: 軌跡をキー単位（キー間隔 = 1）に直し、近すぎる点（0.08 未満）を間引く。長さ 1 未満はタップとして捨てる。
2. 始点・終点の近く（中心間距離 1.3 以内、最大 4 キー）のキーで、索引の箱（先頭キー × 末尾キー）を絞り込む。
3. 箱の各項目（読みのキー経路）を、軌跡から各キーまでの最短距離・長さの比・「キーを経路の順に軌跡の点へ割り当てた距離」
   （簡易 DTW）の表引きだけで枝刈りし、事前確率（語コスト）と合わせた点数の上位 1500 を残す。割り当ての計算は 1 ストロークあたり
   最大 12000 項目（箱は始点・終点に近い順、箱の中は語コストの小さい順なので、上限に達すると珍しい読みから諦める）。
4. 32 点の粗い照合で上位 96 を残し、200 点の本照合で順位付けする（SHARK2 系）:
   形状距離（バウンディングボックスの長辺 1 に正規化した 2 つの折れ線の対応点の平均距離、σ = 0.07）と
   位置距離（キー単位の対応点の平均距離、σ = 0.5）のガウスの対数尤度に、語頻度の事前確率（`-0.2 × 語コスト / 500`）を足す。
   位置距離 1.0・形状距離 0.25 を超える読みは捨てる。
5. 上位 N 個の読みをスコアつきで返す。

綴りの揺れは代表の綴り（`si` `ti` `tu` `hu` `zi` `sya` など最短）に正規化し、ヘボン式（`shi` `chi` `tsu` `fu` `ji` `sha`）も第 2 の経路として
照合する。同じキーが続く並び（促音の子音重ね `kk`、撥音の `nn`、母音の連続）は 1 つのキーにまとめ、「小さなループ付き」の経路も
照合して良い方を採る。長音 `ー` はキーが無いので飛ばす。ひらがな以外を含む読みと、キーが 1 つしかない読みは索引に入らない。

### 索引

- 辞書（`nagi-dict.bin`）の全読みから作る。`cargo xtask build-glide-index` が `data/dict/nagi-glide.bin` を作り（1.6 秒）、
  サーバーは起動時にこのファイルがあれば mmap で読む。**無ければ最初のなぞり入力のときに辞書から作る**
  （メモリ上、約 1.3 秒・約 39MB。その間エンジンのロックを持つ。デスクトップ向けの縮退）。
  **ファイル専用モード**（`--glide-index-file-only` / FFI の `NAGI_FLAG_GLIDE_INDEX_FILE_ONLY`。iOS 拡張が使う）では
  辞書から作らず、ファイルが読めるまで「グライド利用不可」（`glide_input` は `consumed = false`）。ファイルは認識のたびに
  （無い間だけ）探し直すので、後から置かれた索引は次のなぞりから使える。壊れた・書きかけのファイルは使わない。
- **iOS への配布（H-84）**: ホストアプリが `nagi_build_glide_index(dict_path, out_path)`（FFI。一時ファイル → rename、約 2 秒、
  ピークのメモリ約 180MB）で App Group の `data/dict/nagi-glide.bin` に作る。辞書との整合は付属ファイル `nagi-glide.meta`
  （辞書のサイズ・更新時刻・索引のサイズ）で判定し、辞書を更新したら作り直す。自動で作るのは `input.glide` がオンのときだけ
  （オンにしたとき・ホームを開いたとき・辞書の更新時）。手動のボタンはホームと設定にある。拡張は索引があるときだけなぞりの
  ジェスチャを有効にする。
- 形式（`core/glide/src/index.rs` 先頭）: 箱の表、固定長の項目（12 バイト）、読みとキー経路のプール。各配列は要素ごとに読むので
  アラインメント不要で mmap できる。辞書を作り直したら索引も作り直す。
- サイズ（Mozc OSS 辞書: 745,964 読み → 1,091,631 項目。ヘボン式で先頭キーが変わる・経路が変わる読みは複数の項目）:
  **39.17 MB**。mmap なので常駐は触れたページだけ。1 ストロークが触れるのは箱 16 個ぶん（走査 5〜8 万項目 ≈ 1〜2MB）。
  1200 ストローク後でも常駐の増分は +34MB 程度（ランダムな読みで全域を触るため。実際の入力は箱が偏る）。
  iOS 拡張での実測は未実施（H-7 の辞書の mmap と同様に、クリーンページは拡張のフットプリントにほぼ載らない想定）。
- 縮小の余地（未実施）: 読みのプール（約 10MB）を 1 バイト符号にする、ヘボン式の経路を持たず読みから都度作る、
  語コストが高い（珍しい）読みを除く。

## 3. 評価

```sh
cd core
cargo xtask fetch-dict && cargo xtask build-dict && cargo xtask build-glide-index
cargo run --release -p nagi-glide --bin nagi-glide-eval -- --data-dir ../data --index ../data/dict/nagi-glide.bin \
    [--n 1000] [--seed 21] [--noise clean,normal,noisy] [--sampling uniform,weighted] [--verbose]
```

合成軌跡（`nagi_glide::synth`、シード固定）の生成: 読みの理想経路（ヘボン式 30%・ループ 30〜50%）の各キーに狙いのずれ
（σ = 0.12 / 0.22 / 0.35 キー）と全体の偏りを加え、Catmull-Rom 曲線でつなぎ、区間ごとに所要時間をばらつかせて 60〜90 Hz で
サンプリングし、点を 10 / 20 / 35% 間引く。ノイズの段階は clean / normal / noisy。読みは辞書の対象 744,198 読みから、
一様（uniform）または語頻度に比例（weighted。`exp(-語コスト / 500)`。実際の入力の分布に近い）で選ぶ。

結果（リリースビルド、このサンドボックスの Xeon 2.1GHz、`--seed 21 --n 1000`、`--index` で mmap）:

| 読みの選び方 | ノイズ | top1 | top5 | top10 | 認識時間 p50 / p95 / max |
| --- | --- | --- | --- | --- | --- |
| 語頻度 | clean | 88.1% | 99.7% | 99.9% | 3.9 / 10.7 / 18.9 ms |
| 語頻度 | normal | 78.2% | 98.0% | 99.3% | 3.4 / 11.7 / 21.5 ms |
| 語頻度 | noisy | 59.5% | 83.2% | 87.3% | 2.3 / 9.8 / 20.4 ms |
| 一様 | clean | 50.2% | 73.1% | 79.9% | 9.6 / 17.1 / 26.3 ms |
| 一様 | normal | 44.3% | 69.1% | 76.3% | 10.5 / 19.2 / 35.0 ms |
| 一様 | noisy | 26.4% | 45.7% | 53.8% | 9.4 / 16.9 / 29.3 ms |

- 一様は珍しい語（固有名詞など）が多く、事前確率が効かないので低い。実際の使い方に近いのは語頻度のほう。
- 「無応答」（フィルタで全部落ちた）は語頻度で 0〜2%、noisy で 2%、一様の noisy で 7%。
- 目標（1 ストロークの認識 p95 < 50ms）は、この環境では満たす。実機（特に Android の中位機）では未測定。
  `max_aligned`（割り当てを計算する項目数の上限）が時間と珍しい語の精度の調整つまみ（6000 で p95 が約半分、uniform の top5 は約 10 ポイント下がる）。
- 測定の限界: ノイズは自作の生成モデル由来で、実際の指の挙動（利用者ごとの癖・速い急ぎ書き・親指の弧）より楽観的。
  σ・事前確率の重みは seed 11 で調整して seed 21 で測ったが、同じ生成モデルなので過学習の可能性がある。**実機の軌跡で取り直すこと。**
- 回帰テスト: `core/glide/tests/accuracy.rs`（小さな語彙 + 偽の読み 4000 でノイズ別の下限をアサート。辞書があれば実辞書の
  語頻度 top5 ≥ 92% も確認）、`core/engine/tests/glide.rs`、`core/server/tests/glide.rs`（JSON-RPC。LLM 無し・偽モデル付き）。

## 4. 未決・未実装

- G3（Android）: フロントの UI（軌跡の描画、タップ・長押しポップアップ・スペーススライド・フリックとの競合整理、`glide_input` の送信）。G4（iOS）は実装済み（H-83）。
- iOS への索引 `nagi-glide.bin` の配布は実装済み（H-84。**実機・Swift の CI 未確認**）。Android は未着手（JNI はフラグを渡しておらず、無ければ辞書から作る従来の挙動）。
- 連続なぞり（複数語）、ライブ変換との併用、学習への反映（グライドの読みの選択履歴を事前確率に足す）、左文脈による読み候補の再採点（G5）。
  現状の左文脈は、読みの変換（zenz）にだけ効く。
- 実機の軌跡での σ・しきい値の調整。座標の個人化（偏りの補正）は H-25 のプライバシー方針に従い未検討。
- Kotlin の `CandSource`（`Protocol.kt`）に `glide` は足していない（未知の値は `UNKNOWN` に落ちる）。G3 で足す。
